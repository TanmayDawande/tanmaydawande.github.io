I learnt in the computer networks class about sockets in python for the first time. I liked the concept and wanted to explore further on how these things really work behind the scenes. Some interest in cryptography led me to take this on.

First off, I built the basic to-and-fro chat interface with a **`client.py`** and a **`server.py`**. No encryption, no nothing fancy. Both the client and server connected to the same port and ip and the connection was established, just like that. The client sent a message, the server received the message and replied to it accordingly.

## stage 1 - length-prefixed framing

### the problem
Now, this is a very trivial problem. Every time, the `socket.recv()` was hardcoded to receive 1024 bytes by default. This meant that even if the client sends a message that has just 2 bytes in it, ":)" for example, the server does not dynamically know that it's 2 bytes. This also means that when a message is more than 1024 bytes, it gets split across multiple `.recv()` calls and a loop is needed to reassemble it.

### the fix
I thought about creating a packet, whose architecture went like:

`packet = header + actual data`

The point of the header being that it would contain the number of bytes the data is. This is helpful in such a way that `socket.recv(4)` only reads the first 4 bytes, and then decides, based on that, how many more bytes it needs to receive to actually get the data. The 4-byte header and the binary data were packed into one using `struct` in python. This told the receive function to dynamically set the size of the payload.

```
+----------------+----------------------------------+
|  length (4B)   |         payload (N bytes)         |
|  e.g. 0x012C   |     exactly N bytes, no more      |
+----------------+----------------------------------+
```

## stage 2 - RSA encryption

Chat was established successfully after stage 1. The main issue arises now: messages are not encrypted. To tackle this in the most basic terms, I decided to implement RSA encryption. Not just RSA from any library, but understanding the raw math behind how it actually encrypts messages and prevents an interceptor from reading them.

### the threat model

```
client -----------------  server
           |
           |
      eavesdropper
```

The client wants to send the server a message that only the server can read. The server generates a public/private key pair and sends the public key over. Anyone listening on the wire, the eavesdropper, gets that same public key too, but a public key can only encrypt, not decrypt. The client encrypts with it, sends the ciphertext, and only the server's private key can turn it back into the original message.

### the math

We start by generating two distinct massive prime numbers P and Q (using `pycryptodome`'s Miller-Rabin primality test) and multiplying them to get N. N is the key size, or the modulus.

The public key is the pair of two numbers (N, e).

Euler's Totient function is defined as:

`ϕ(N) = (P-1)*(Q-1)`. This function calculates the amount of numbers coprime with N.

To pick the public exponent 'e', it must meet these two criteria:

- `1 < e < ϕ(N)`
- e must be coprime with `ϕ(N)`

To mathematically choose the private key 'd', we use the Extended Euclidean Algorithm to ensure that:

- `(d*e) mod(ϕ(N)) == 1`

The encryption formula is: `C = (M^e) mod N`
The decryption formula is: `M = (C^d) mod N`

### how it plays out in babel

1. The server generates its own keys and sends them to the client
2. The client receives these keys and stores them, and generates its own keys to send to the server
3. The server receives these keys and sends an ACK
4. The ACK is received and the chat begins
5. The client's messages are encrypted with the server's keys and sent
6. The server receives them and decrypts using its own keys

## stage 3 - hybrid encryption with AES-GCM

### the problem

babel used pure RSA modular exponentiation to encrypt chat payloads. Because of the mathematical rules of RSA (M^e mod N), the integer representation of the message (M) must be strictly smaller than the modulus (N).

According to the math, we see that:

- generated primes p and q are 1024 bit
- mod n is 2048 bit
- 2048 bits / 8 bits = 256 bytes

This meant that if a message longer than 256 bytes is sent, an overflow error is caused by the wrap-around logic of the modulus operation. This was a real issue and limited usability.

### the fix

babel was set to use a hybrid cryptography model. This meant RSA would only be used during the handshake, and once a session is established, the actual chat stream would be encrypted using AES-GCM, which has no payload limit and is also more secure. RSA is used to exchange the keys, and after that a secure AES-GCM encrypted session is set up.

### how AES-GCM actually works

ECB mode in the AES scheme uses only one block cypher to take in plaintext and spit out ciphertext. It is very weak.

Counter mode uses a random initializer to ensure that the encryption scheme is different every time. You encrypt the counter, not the message. We XOR the actual message with this encrypted counter and get ciphertext 1 (c1) through cn. Now this is risky: if an attacker gets hold of the ciphertext, they can change the bits, and when the message is decrypted, it will alter the message content itself. We need to add something like a checksum to ensure the CT hasn't been tampered with. We could define a tag that will change even if one of C1-Cn changes. We want to authenticate the ciphertext, obv. We also want to authenticate the length of the message against the tag. AES-GCM first calculates the hash key:

- To generate this, take 128 0s and encrypt that using AES, which gives us H, the hash key
- For each ciphertext, we add it to the existing tag, and multiply it by H (we use finite field arithmetic in the Galois field, too complex for me to explain here)

and voila! Just like that, you can send even a 500-word message with ease, and more security.

## stage 4 - cleanup (SecureNODE)

Things added to make it better for aesthetic and visibility purposes :)

### the SecureNODE class

To clean up the codebase and make it scalable, all the messy networking plumbing (struct packing/unpacking) and the math (RSA/AES) was moved into a dedicated `SecureNODE` class.

The client and server files now just handle the UI and the socket lifecycle. They create a `SecureNODE` object, pass the socket into it, and just call clean functions like `NODE.aes_pack_and_encrypt()`. This keeps the state, like the specific keys for that session, isolated inside the object.
