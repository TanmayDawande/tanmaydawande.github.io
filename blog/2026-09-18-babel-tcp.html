1) Architecture

A-----------------B
        |
        |
        C

A wants to securely receive messages from B. C wants to intercept them. A generates a public and a private key. It sends the public key to B. B and C receive the public key. B uses A’s public key to ENCRYPT the message. C cannot read it. A receives the message and uses A’s private key to DECRYPT it.

2) RSA Encryption Mathematics

Two distinct massive prime numbers P and Q are generated (using pycryptodome’s Miller-Rabin primality test) and multiplied to generate N. N is the clock size or the modulus.

The public key is the pair of two numbers (N, e).

Euler’s Totient function is defined as:

ϕ(N) = (P-1)*(Q-1). This function calculates the amount of numbers coprime with N.

To pick the public exponent ‘e’, it must meet these two criteria:

  • 1 < e < ϕ(N)
  • e must be coprime with ϕ(N)

To mathematically choose the private key ‘d’, we use the Extended Euclidean Algorithm to ensure that:

  • (d*e) mod(ϕ(N)) == 1

The encryption formula is: C = (M^e) mod N The decryption formula is: M = (C^d) mod N

3) Application Layer Protocol (Framing)

Added a 4-byte header to the start of each packet that denotes the length of the entire payload and dynamically tells the socket.recv() function exactly how many BYTES to fetch, preventing TCP buffer overflow/underflow.

This is achieved by using the built-in struct library in Python that packs the length of the message into a 32-bit network-byte-order integer (!I). The receiver first reads the 4-byte header, unpacks it to get the integer length, and then dynamically receives the exact remainder of the packet.

added the two way rsa encryption. Earlier, only client messages we encrypted but now the client also has its messages encrypted. Made a new crypto_engine that handles the separate logic of encrypting and decrypting

logic steps involved -

  1. The server generates its own keys and sends them to the client
  2. The client recieves these keys and stores them and generates its own keys to send them to the server
  3. The server recieves these keys and sends an ACK
  4. The ack is recieved and the chat begins
  5. The client messages are encryoted by the servers keys and sent
  6. The server recieves them and decrypts using its own keys.

PROBLEM OCCOURED -

currently, babel uses pure RSA modular exponentiation to to encrypt chat payloads. Because of the mathematical rules of RSA (M^e mod N), the Integer representation of the Message (M) must be strictly smaller than the Modulus (N).

  • generated primes, p and q are 1024 bit
  • mod n is 2048 bit
  • 2048 bits / 8 bits = 256 bytes

BUG - if a message more than 256 bit is sent, an overflow error is caused due to wrap-around logic of modulus operation

FIX - babel will use a hybrid cryptography model in the futire commits. RSA will only be used duing handshake and after that once a session is established, the actual chat stream will be encrypted using AES-GCM, which has no payload limit.

AES - GCM (Advanced Encryption Standard in Galois/Counter Mode)

ECB mode in the AES scheme uses only one block cypher to take in plaintext and spit out cyphertext. It is very weak.

Counter mode uses a random initializer to ensure that the encryption scheme is different everytime. You encrypt the counter not the message. We will XOR the actual message with this encrypted counter and get cyphertext 1(c1) to cn. Now this is risky. If an attacker gets hold of the cyphertext, they can change the bits and when the message is drcrypted, it will alter the message content itself. We need to add something like a checksum to ensure that the CT hasnt been tampered with. We could define a tag that will change even if one of the C1-Cn changes (cyphertext). We want to authenticate the cyphertext, obv. We also want to authenticate the length of the message against the tag. aes-gcm first calculates the hash key first.

  • To generate this, 128 0s and we encryot that using aes, that gives us H, the hash key
  • For each cyphertext, we add it to your existing tag, multiply it to H (We use finite field arithmetic in the Galois field..too complex for me to explain)

Object-Oriented Refactoring (SecureNODE)

To clean up the codebase and make it scalable, all the messy networking plumbing (struct packing/unpacking) and the math (RSA/AES) was moved into a dedicated SecureNODE class.

The client and server files now just handle the UI and the socket lifecycle. They create a SecureNODE object, pass the socket into it, and just call clean functions like NODE.aes_pack_and_encrypt(). This keeps the state (like the specific keys for that session) isolated inside the object.
